# Proposal — `GET /repos/:id/stats` (30-day review-activity rollup)

| repo-relative path | new / modified | what goes in it and why it belongs there |

| `server/src/vendor/shared/contracts/repo-stats.ts` | **new** | The `RepoStats` Zod contract (`repo_id`, `since`, `runs`, `findings_total`, `findings_by_severity`). | `server/src/modules/repos/repository.ts` | modified | Adds the two read-only aggregate queries — `countRunsSince()` (`agent_runs ⋈ pull_requests`) and `findingsBySeveritySince()` (`findings ⋈ reviews ⋈ agent_runs ⋈ pull_requests`, `GROUP BY severity`) — plus the `SeverityCount` row type. | `server/src/modules/repos/service.ts` | modified | Adds `stats(workspaceId, repoId)`: the tenancy/existence check (`getById` → `NotFoundError`), computes the window boundary, fires the two aggregates in parallel, and returns the DTO. Business logic and the 404 decision belong in the service, not the route. |
| `server/src/modules/repos/routes.ts` | modified | Registers `GET /repos/:id/stats` with `params: IdParams` + `response: { 200: RepoStats }` (server convention: every route validates and serializes through Zod), resolves tenancy via `getContext`, and delegates straight to `service.stats`. Adds the route to the module's doc-comment route table. No new module registration is needed — `repos` is already wired in `modules/index.ts`. |

No schema/migration change: everything the endpoint needs (`agent_runs.ran_at`, `agent_runs.workspace_id`, `reviews.run_id`, `findings.severity`, `pull_requests.repo_id`) already exists.

## Runtime flow

A request to `GET /repos/<uuid>/stats` hits the `repos` Fastify plugin, where the Zod type-provider validates `:id` as a uuid (an invalid id 422s at the edge) and `getContext(container, req)` resolves `workspaceId` through the `AuthProvider`. The route calls `RepoService.stats(workspaceId, repoId)`, which first loads the repo through `RepoRepository.getById(workspaceId, repoId)` — a repo from another workspace is indistinguishable from a missing one and throws `NotFoundError` (404), keeping the endpoint IDOR-safe. It then derives `since = now − STATS_WINDOW_MS` and runs the two repository aggregates concurrently: `countRunsSince` counts `agent_runs` rows (any status — failures are part of the run history) joined to `pull_requests` of that repo with `ran_at >= since`, and `findingsBySeveritySince` walks `findings → reviews → agent_runs → pull_requests` for the same repo/window and groups by severity. Both carry `agent_runs.workspace_id = :workspaceId` in their `WHERE`, so tenancy is enforced in SQL and not only by the pre-check. The raw counts go to the pure `toRepoStatsDto`, which zero-fills the severity buckets and sums `findings_total` from the same grouped rows (so the total always equals the sum of its parts), and the resulting object is serialized by the route's `RepoStats` response schema.

## Decisions worth flagging

- **Param name.** The request said `/repos/:repoId/stats`; I registered `/repos/:id/stats`. The URL clients call is identical — only the internal param name differs — and `:id` reuses the shared `IdParams` schema and matches every other route in the module (`/repos/:id/file`, `/refresh`, `DELETE`). (Fastify 5's router would in fact accept `:repoId` alongside `:id`, since find-my-way 9 stores param names per handler; this is a consistency choice, not a technical constraint.) Say the word and it becomes `:repoId`.
- **A finding's window is its run's window.** `findings` has no timestamp of its own, so a finding counts as "last 30 days" when the run that produced it ran in the last 30 days. That is also what makes `runs` and `findings_total` describe the same population.
- **`kind = 'review'` filter** on the findings join mirrors the existing per-run severity rollup in `reviews/repository/run.repo.ts`; today only `kind: 'review'` rows are ever inserted, so it changes nothing now and prevents double-counting if summary reviews ever carry findings.
- **Client contract copy.** `client/src/vendor/shared/` is a synced mirror of the server contracts. Nothing in the client consumes this endpoint yet, so I did not touch it; if/when a UI lands, `contracts/repo-stats.ts` + the barrel line must be mirrored there.
