# Proposal — Slack summary when a review run finishes

## Files

| Path | New / Modified | What goes in it and why it belongs there |
|---|---|---|
| `server/src/adapters/notify/slack.ts` | **new** | The `Notifier` port (`reviewFinished(notice)`) + its Slack implementation `SlackWebhookNotifier`, plus the pure `formatReviewFinished` message builder. Every external call in this codebase sits behind an adapter interface (`GitHubClient`, `LLMProvider`, `DepGraph`, `Tokenizer`), so an outbound HTTP POST to Slack belongs here too — the run executor depends on the interface, not on `fetch`. Interface + impl co-located in `adapters/<name>/` follows the `depgraph`/`tokenizer` precedent (server-only ports live with their adapter; `vendor/shared/adapters.ts` is the do-not-touch, cross-package contract file and Slack is not cross-package). The notice is domain-shaped (`repo`, `prNumber`, `agentName`, `findings`, `bySeverity`) so Slack vocabulary — webhooks, mrkdwn, escaping — never leaks out of this file. |
| `server/src/platform/container.ts` | modified | Composition root: `ContainerOverrides.notifier` + a lazy `get notifier()` that constructs `SlackWebhookNotifier` with a **resolver closure** `() => this.secrets.get('SLACK_WEBHOOK_URL')`. This is the only place a concrete is wired (same rule as every other adapter), and the closure — mirroring how `priceBook` resolves `OPENROUTER_API_KEY` — means the secret is read on each send, so a key added at runtime via Settings works with no `invalidateSecretCaches` change. |
| `server/src/adapters/index.ts` | modified | One export line in the adapter barrel, consistent with the other adapters. |
| `server/src/modules/reviews/helpers.ts` | modified | `countBySeverity(findings): Record<Severity, number>` — the "split by severity" rule. `helpers.ts` is explicitly the module's pure, side-effect-free helper file (it already holds `taskLine`, the DTO mappers), so the counting logic is testable without a container and the executor stays orchestration-only. |
| `server/src/modules/reviews/run-executor.ts` | modified | The trigger. `runOneAgent` already owns "a run finished": after `completeAgentRun(... status: 'done')` it calls a new private `notifyRunFinished(...)`, which builds the notice from data it already has (`repo.fullName`, `pull.number`, `agent.name`, the kept findings) and hands it to `container.notifier`. It swallows errors into a Live Log line — identical to the existing best-effort enrichments (`buildCallersDigest`, `buildSpecBlocks`): a broken webhook must never fail a run whose review is already persisted. |
| `server/.env.example` | modified | Documents `SLACK_WEBHOOK_URL` next to the other keys. It is a **secret**, so it is deliberately *not* added to `AppConfig`/`EnvSchema` — `config.ts` states that secrets go through `SecretsProvider`, whose `LocalSecretsProvider` reads `~/.devdigest/secrets.json` with `process.env` as fallback. That is exactly "from config like the other secrets do", and it needs no code change to `SecretKey` (the union ends in `(string & {})`, and `vendor/shared` is do-not-touch). |

## Runtime flow

`POST /pulls/:id/review` → `ReviewService.runReview` creates the `agent_runs` rows and fires `ReviewRunExecutor.executeRuns` in the background. For each agent, `runOneAgent` runs the pure engine (`reviewPullRequest`), persists the review + findings, marks the PR reviewed, and calls `repo.completeAgentRun(runId, { status: 'done', … })`. Immediately after that — the point at which the run is officially finished — it calls `this.notifyRunFinished(repo, pull, agent, keptFindings, runLog)`, which shapes a `ReviewFinishedNotice` (repo full name, PR number, agent name, total findings, `countBySeverity(...)` from `helpers.ts`) and passes it to `container.notifier`. The container hands back `SlackWebhookNotifier`, which resolves `SLACK_WEBHOOK_URL` through `SecretsProvider`; if it is unset the call returns immediately (feature off, zero behaviour change), otherwise it formats a one-line mrkdwn summary — `*owner/repo #42* — review by "Security Reviewer" finished: 5 finding(s) — 1 critical · 3 warning · 1 suggestion` — and POSTs `{ text }` to the webhook via `fetch`, wrapped in the project's `withTimeout`/`withRetry` primitives (5 s, one retry on 429/5xx). A non-2xx or timeout throws out of the adapter, is caught by `notifyRunFinished`, and becomes a `notify: failed to post run summary — …` line in the run's Live Log/trace; the run itself still completes as `done`. One run = one agent, so an "all agents" review posts one message per agent — hence the agent name in the message.

Notes: failed/cancelled runs do not notify (nothing "came back"). Tests are unaffected without any mock — with no `SLACK_WEBHOOK_URL` set the notifier no-ops — and a fake can still be injected via `ContainerOverrides.notifier`.
