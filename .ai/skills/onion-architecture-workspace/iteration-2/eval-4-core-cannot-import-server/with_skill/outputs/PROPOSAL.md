# Proposal — reviewer-core reports its pipeline stage; the Live Log shows it live

## Files

| Repo-relative path | New / modified | What goes in it and why it belongs there |
|---|---|---|
| `reviewer-core/src/review/run.ts` | modified | The engine's progress vocabulary and the stage emissions. Adds `export type ReviewStage = 'diff-parsed' \| 'prompt-assembled' \| 'llm-called' \| 'findings-grounded'`, adds an optional `stage` to the existing `ReviewEvent`, and emits one stage event at each of the four boundaries — **before** the awaited LLM call, not after it. This is the **domain/core ring**: the stage names are the engine's own pipeline in the engine's own terms. The core still performs no I/O — the events leave through the already-injected `onEvent` sink, so `reviewer-core` never learns that a run, a run bus, or SSE exists (skill hard rules 1 & 2 — the core imports nothing outward; `dependency-rule.md` forbidden-imports checklist). Size is reported in **chars**, not tokens, on purpose: a token count would need the `Tokenizer`, which is a server-side adapter — the core must not reach for it. |
| `reviewer-core/src/index.ts` | modified | Barrel export of the new `ReviewStage` type alongside `ReviewEvent`. The server must *name* the type to forward it, and the public API of the pure package is where callers get it from. |
| `server/src/modules/reviews/helpers.ts` | modified | New `runEventData(e: ReviewEvent)` — **boundary mapping** from a core `ReviewEvent` to the `data` payload the server publishes on the run bus (merges `stage` in as a machine-readable tag). The skill's decision table puts boundary conversions in `modules/<name>/helpers.ts` (rule 5); it keeps the translation out of both the core (which must stay ignorant of run events) and the executor (which stays orchestration). Pure function — no `this`, no I/O — matching the file's existing contract. |
| `server/src/modules/reviews/run-executor.ts` | modified | One-line change in the `onEvent` lambda passed to `reviewPullRequest` (`runLog.event(e.kind, e.msg, runEventData(e))`) plus the comment that documents the seam. This is the **application ring**: it is the only place that knows both the engine and the `RunLogger`, so it is where the engine's progress port gets adapted onto the server's streaming infrastructure. |

**Deliberately NOT changed:**

- `server/src/vendor/shared/contracts/trace.ts` — no new `RunEventKind`, no `ReviewStage` in the shared contracts. The skill's test for `vendor/shared` is "*does any package outside `server/` have to name this type?*" Nothing outside does: the stages surface as ordinary `info`/`tool`/`result` run events whose `msg` the Live Log already renders, and `RunEvent.data` is already `z.unknown()`, so the stage tag rides along with no contract change. Parking the type in the hand-synced, client-mirrored `vendor/shared` would widen that surface for nothing (`SKILL.md` — *Where does the port interface go?*).
- `server/src/platform/run-logger.ts` / `sse.ts` — the generic run-log/SSE infrastructure gains no knowledge of the review engine.
- `client/` — the Live Log (`LiveLogStream` via `RunStatus`) already renders every streamed `RunEvent` as `[t] [kind] msg` as it arrives; stage events are just more of them, so they appear in real time with zero UI work.
- The existing `Citation grounding: <summary>` message text is preserved (only tagged with `stage: 'findings-grounded'` + counts) so the current reviewer-core event assertion still holds.

## How the pieces call each other at run time

The route queues the run and returns immediately; `ReviewRunExecutor.runOneAgent` (application) resolves the LLM port from the `Container`, builds the prompt context, and calls the pure `reviewPullRequest` — passing, as it already did, an `onEvent` lambda closed over the run's `RunLogger`. That lambda is the whole adapter: the **core defines the shape of a progress event and calls back**, the **server decides where it goes**. Inside the engine, each stage boundary now fires that callback synchronously as it is reached — `diff-parsed` after the diff is ingested and the mode chosen, `prompt-assembled` after each chunk's messages are built, `llm-called` immediately *before* `await llm.completeStructured(...)` (the long, silent stretch that made the UI look frozen), and `findings-grounded` after the citation gate. Each callback runs `runEventData(e)` (helpers) to fold the stage into the payload, then `RunLogger.event(kind, msg, data)` fans it out to `RunBus.publish(runId, …)`, which pushes it onto the run's in-memory buffer and emits it to the open `GET /runs/:id/events` SSE subscriber; the client's `useRunEvents` appends it and `LiveLogStream` paints the line — so the four stages land in the Live Log the moment they happen rather than at the end. The same buffer is what gets persisted as `run_traces.log` on completion, so the stage lines survive a reload too. The dependency arrows all point inward: `run-executor` → `reviewer-core` → nothing; `reviewer-core` never imports `platform/sse.js`, `RunLogger`, the `Container`, or a `runId` — swap the SSE bus for a CLI printer (as the CI runner does) and the engine is untouched.
