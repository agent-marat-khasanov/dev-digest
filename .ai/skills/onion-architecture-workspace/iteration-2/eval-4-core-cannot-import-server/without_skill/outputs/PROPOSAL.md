# Proposal — stage reporting from `reviewPullRequest` into the Live Log

## Files

| repo-relative path | new or modified | what goes in it and why it belongs there |
|---|---|---|
| `reviewer-core/src/review/run.ts` | modified | The whole feature. Adds an exported `ReviewStage` union (`diff_parsed` \| `prompt_assembled` \| `llm_called` \| `findings_grounded`) and an `emitStage()` helper, then tags the four pipeline boundaries as the engine crosses them. This is the only file that knows the pipeline's shape, so it is the only file that can say which stage the run is on. `llm_called` is emitted **before** the provider call (that is the stage a long run actually sits in) and the per-chunk result line now carries the model's elapsed seconds. Emission goes through the already-existing injected `onEvent` sink — no new dependency, no I/O, so the module stays pure. |
| `reviewer-core/src/index.ts` | modified | One added line: re-export `type ReviewStage` from the barrel. `ReviewEvent` is already public API here; the stage vocabulary that rides on it must be public too, so the server (and the CI runner) can name the stages in a type-safe way instead of string-matching log text. |

**No server, shared-contract, or client file changes.** See "Why nothing else moves" below — this is deliberate, not an omission.

## How the pieces call each other at run time

`ReviewRunExecutor.runOneAgent` (`server/src/modules/reviews/run-executor.ts:212`) already calls `reviewPullRequest({ …, onEvent: (e) => runLog.event(e.kind, e.msg, e.data) })` — an injected progress **sink** the engine calls but knows nothing about. During a run, the engine now fires `onEvent` at each boundary: once with `diff_parsed` as soon as it has sized the diff and picked single-pass vs map-reduce; then, per chunk, `prompt_assembled` right after `assemblePrompt()` and `llm_called` immediately before `llm.completeStructured()` (so the "waiting on the model" stage is on screen *while* we wait, not after); then a `result` line with the findings count and how many seconds the model took; and finally `findings_grounded` once the citation gate has run. Each call lands in `RunLogger.event()` (`server/src/platform/run-logger.ts:50`), which fans it out to `RunBus.publish()` (`server/src/platform/sse.ts:52`) and mirrors it to pino. The bus stamps `seq` + `t` and pushes a `RunEvent` to the SSE stream on `GET /runs/:id/events` (`server/src/modules/reviews/routes.ts:49`), where the client's `useRunEvents` (`client/src/lib/hooks/reviews.ts:168`) appends it to state and `RunStatus` renders it through `LiveLogStream` — colour-coded by `kind` (`tool` = amber for the LLM wait, `result` = green for grounding). Because the events flow through a live bus rather than being returned at the end, the lines appear as the stages happen; the same events are also captured in the run's buffer and persisted into `run_traces.log`, so the stage history survives a reload.

The machine-readable stage rides on the event's existing `data` payload (`{ stage, …extra }`), which the executor already forwards verbatim and `RunEvent.data` (`z.unknown().optional()`) already carries to the browser — so the SSE wire gains the stage marker with zero contract churn, while the human-readable text lives in `msg`, which is what `LiveLogStream` prints today.

## Why nothing else moves

- **`reviewer-core` cannot import from `server/`.** Its tsconfig exposes exactly one cross-package alias — `@devdigest/shared` → `server/src/vendor/shared` (`reviewer-core/tsconfig.json`) — and the module contract is "no DB/fs/network; the only side effect is the injected `LLMProvider`". Reaching for `RunLogger` or `RunBus` to report progress would break both the alias graph and the purity that lets the CI runner bundle this package with ncc. The outbound port for progress already exists (`onEvent`), so the engine reports stages by calling it and stays ignorant of SSE entirely.
- **`server/src/vendor/shared/` is Do-Not-Touch** (CLAUDE.md), so `ReviewStage` is declared in reviewer-core — the package that *produces* the vocabulary — rather than added as a Zod enum next to `RunEventKind`. Nothing on the wire needs a schema change, because `RunEvent.data` is already `unknown`.
- **`client/src/vendor/ui/LiveLogStream.tsx` is Do-Not-Touch** and already renders any event it receives. The stage lines therefore show up with no client change; I did not add a stage "chip" to the UI, since that would mean editing the vendored kit and no one asked for it.
- The other two engine callers (`server/src/modules/review-working/service.ts:33`, `server/src/modules/evals/service.ts:92`) pass no `onEvent`; the sink is optional, so they are unaffected.
- Behaviour is otherwise unchanged: prompt assembly moved a few lines earlier inside the loop (it is pure, so this is a no-op) purely so `prompt_assembled` can precede `llm_called`, and the existing `'Citation grounding: …'` message text is preserved — `reviewer-core/test/run.test.ts:69` asserts on it.

**Known gap, not fixed here:** if a single model call runs for minutes, the log will sit on the `llm_called` line for that whole time — correct, but still a static screen. A true heartbeat (periodic tick or token streaming) is a bigger change than "report which stage it's on" and I left it out of scope; `LiveLogStream` does already show a running pulse + elapsed label meanwhile.
